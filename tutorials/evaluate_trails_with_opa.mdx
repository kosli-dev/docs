---
title: "Evaluate trails with OPA policies"
description: "Learn how to write safe OPA/Rego policies and evaluate Kosli trails against them with kosli evaluate policy, including design rules that prevent false-positive compliance results."
---

The `kosli evaluate policy` command lets you evaluate Kosli trails against custom policies written in <Tooltip tip="Rego is the purpose-built declarative policy language used by the Open Policy Agent (OPA) project. It is designed for expressing rules over structured data and is widely used for policy enforcement in cloud-native environments." cta="Learn more" href="https://www.openpolicyagent.org/">[Rego](https://www.openpolicyagent.org/docs/latest/policy-language/)</Tooltip>. This is useful for enforcing rules like "every artifact must have an approved pull request" or "all security scans must pass", and for gating deployments in CI/CD pipelines based on those rules. Kosli evaluates the policy on the server, against the trails as Kosli recorded them, and the CLI prints the result.

<Note>
`kosli evaluate trail` and `kosli evaluate trails` are deprecated. Use `kosli evaluate policy --context trail=<flow>/<trail>` instead. The older commands evaluate the policy in the CLI and pass it a different input. See [Local evaluation](/policy-reference/rego_policy#local-evaluation) for the differences.
</Note>

In this tutorial, you'll write and evaluate policies against trails in your own Kosli org. Along the way, you'll learn three design rules that prevent a Rego policy from granting false-positive compliance results.

<Steps>

<Step title="Prerequisites">

To follow this tutorial, you need to:

* [Install Kosli CLI](/getting_started/install).
* [Get a Kosli API token](/getting_started/authenticating_to_kosli).
* Have a flow with a few trails that carry a pull request attestation, and a trail with a Snyk container scan attestation for the later steps.
* Set the `KOSLI_API_TOKEN` and `KOSLI_ORG` environment variables:

  ```shell
  export KOSLI_API_TOKEN=<your-api-token>
  export KOSLI_ORG=<your-org>
  ```

<Info>
Kosli runs the policy with a built-in Rego evaluator, so you only need to write a `.rego` policy file. You need OPA installed only to test a policy on your machine with `opa eval`, as in the step on passing parameters.
</Info>

</Step>

<Step title="Write a policy">

Create a file called `pr-approved.rego` with the following content:

```rego pr-approved.rego
package policy

import rego.v1

pr_attestation_name := data.params.pr_attestation_name

default allow := false

# METADATA
# entrypoint: true
violations contains msg if {
    some trail in input.trails
    some pr in trail.compliance_status.attestations_statuses[pr_attestation_name].pull_requests
    count(pr.approvers) == 0
    msg := sprintf("trail '%v': pull-request %v has no approvers", [trail.trail_name, pr.url])
}

trail_is_approved(trail) if {
    every pr in trail.compliance_status.attestations_statuses[pr_attestation_name].pull_requests {
        count(pr.approvers) > 0
    }
}

allow if {
    every trail in input.trails {
        trail_is_approved(trail)
    }
}
```

This policy applies three design rules that every evaluate policy should follow.

**Rule 1: `default allow := false` (fail safe)**

Trails are denied unless the policy explicitly allows them. Anything the policy cannot positively verify is treated as non-compliant. This matches Kosli's compliance direction: a false non-compliant blocks a good trail (recoverable); a false compliant passes a bad one (not recoverable).

The alias `pr_attestation_name := data.params.pr_attestation_name` reads the attestation name from a params file rather than hardcoding it. Different orgs and flows use different names for their pull-request attestation (for example `"pull-request"` or `"pr"`). If the param is absent, `pr_attestation_name` is undefined, the lookup into `attestations_statuses` fails, `trail_is_approved` does not fire, and `allow` stays `false`. That is the correct fail-safe.

**Rule 2: Drive `allow` via a positive assertion, not the absence of violations**

`allow` fires through `trail_is_approved`, which makes a positive claim: every PR has at least one approver. It is never driven by `count(violations) == 0`.

The following pattern looks equivalent but is not safe:

```rego
# unsafe
allow if {
    count(violations) == 0
}
```

If the `violations` rule body references a field that does not exist (a typo in `pull_requests`, an unexpected schema change, a missing key), the rule body silently produces no messages. The violations set is empty, `count(violations) == 0` is true, and `allow` fires even though no PRs were actually checked. The trail receives a false-positive compliant result.

With the safe pattern, if `pull_requests` is undefined, `every pr in ...` fails to evaluate, `trail_is_approved` does not fire, and `allow` stays `false`.

**Rule 3: Violations provide diagnostics only**

`violations` explains why a policy was denied. It does not decide whether it was denied. When a `violations` rule body encounters an undefined reference, it silently produces no message. This is the safe failure mode: you lose a diagnostic, not a compliance check.

The `# METADATA` and `# entrypoint: true` annotation on `violations` makes Kosli return the rule in the evaluation result, so the CLI can print the messages when the policy denies.

<Info>
See the [Rego Policy reference](/policy-reference/rego_policy) for the full policy contract, input data shape, and exit code behavior.
</Info>

</Step>

<Step title="Evaluate multiple trails">

Evaluate several trails of one flow against the policy. Name each trail with its own `--context trail=<flow>/<trail>`. Kosli evaluates them all at the same instant and passes them to the policy as `input.trails`. Replace the attestation name in `--params` with the name your flow uses for its pull request attestation, such as `"pull-request"` or `"pr"`:

```shell
kosli evaluate policy \
  --path pr-approved.rego \
  --params '{"pr_attestation_name": "pull-request"}' \
  --context trail=my-flow/9978a1ca82c273a68afaa85fc37dd60d1e394f84 \
  --context trail=my-flow/b334d371eb85c9a5c811776de1b65fb80b52d952 \
  --context trail=my-flow/5abd63aa1d64af7be5b5900af974dc73ae425bd6
```

If any pull request has no approvers, the policy denies and the CLI prints the violations. The CLI also prints the policy that ran, by its digest, which is left out of the outputs in this tutorial:

```plaintext
RESULT:      DENIED
VIOLATIONS:  trail '5abd63aa1d64af7be5b5900af974dc73ae425bd6': pull-request https://github.com/my-org/my-repo/pull/342 has no approvers
             trail '9978a1ca82c273a68afaa85fc37dd60d1e394f84': pull-request https://github.com/my-org/my-repo/pull/344 has no approvers
```

When every pull request has at least one approver, the policy allows:

```plaintext
RESULT:  ALLOWED
```

</Step>

<Step title="Evaluate a single trail">

When the context names exactly one trail, Kosli also passes it to the policy as `input.trail`. Use this to check facts within a single trail. For example, you might check that a Snyk container scan found no high-severity vulnerabilities.

Save this as `snyk-no-high-vulns.rego`:

```rego snyk-no-high-vulns.rego
package policy

import rego.v1

default allow := false

artifact_scan_is_clean(artifact) if {
    snyk := artifact.attestations_statuses["snyk-container-scan"]
    every result in snyk.processed_snyk_results.results {
        result.high_count == 0
    }
}

allow if {
    every _, artifact in input.trail.compliance_status.artifacts_statuses {
        artifact_scan_is_clean(artifact)
    }
}

# METADATA
# entrypoint: true
violations contains msg if {
    some name, artifact in input.trail.compliance_status.artifacts_statuses
    snyk := artifact.attestations_statuses["snyk-container-scan"]
    some result in snyk.processed_snyk_results.results
    result.high_count > 0
    msg := sprintf("artifact '%v': snyk container scan found %d high severity vulnerabilities", [name, result.high_count])
}
```

`allow` fires only when `artifact_scan_is_clean` succeeds for every artifact. If `snyk-container-scan` is absent or `processed_snyk_results` is undefined, `artifact_scan_is_clean` fails to fire and `allow` stays `false`. Replace `snyk-container-scan` with the name of the Snyk attestation in your flow.

Evaluate one trail:

```shell
kosli evaluate policy \
  --path snyk-no-high-vulns.rego \
  --context trail=my-flow/44ca5fa2630947cf375fdbda10972a4bedaaaba3
```

```plaintext
RESULT:  ALLOWED
```

The trail has zero high-severity vulnerabilities, so the policy allows it.

<Info>
The full input data shape, including `input.trail` and `input.trails`, is documented in the [Rego Policy reference](/policy-reference/rego_policy#input-data).
</Info>

</Step>

<Step title="Pass parameters to a policy">

Policies often need thresholds that vary by environment, stricter in production than in staging. Use the `--params` flag to pass these values as `data.params` rather than hardcoding them in the policy.

Save this as `snyk-severity-threshold.rego`:

```rego snyk-severity-threshold.rego
package policy

import rego.v1

max_high   := data.params.max_high
max_medium := data.params.max_medium

default allow := false

artifact_within_threshold(artifact) if {
    snyk := artifact.attestations_statuses["snyk-container-scan"]
    every result in snyk.processed_snyk_results.results {
        result.high_count   <= max_high
        result.medium_count <= max_medium
    }
}

allow if {
    every _, artifact in input.trail.compliance_status.artifacts_statuses {
        artifact_within_threshold(artifact)
    }
}

# METADATA
# entrypoint: true
violations contains msg if {
    some name, artifact in input.trail.compliance_status.artifacts_statuses
    snyk := artifact.attestations_statuses["snyk-container-scan"]
    some result in snyk.processed_snyk_results.results
    result.high_count > max_high
    msg := sprintf("artifact '%v': %d high-severity vulnerabilities exceed limit of %d", [name, result.high_count, max_high])
}

violations contains msg if {
    some name, artifact in input.trail.compliance_status.artifacts_statuses
    snyk := artifact.attestations_statuses["snyk-container-scan"]
    some result in snyk.processed_snyk_results.results
    result.medium_count > max_medium
    msg := sprintf("artifact '%v': %d medium-severity vulnerabilities exceed limit of %d", [name, result.medium_count, max_medium])
}
```

**Why the aliases at the top matter**

`max_high := data.params.max_high` is not just shorthand. In the compliance path, `result.high_count <= max_high` is a positive bound check. If `max_high` is absent from the params file, this condition is undefined, `artifact_within_threshold` fails to fire, and `allow` stays `false`. That is the correct fail-safe behavior.

Compare this to a policy that drives `allow` through the absence of violations:

```rego
# unsafe
violations contains msg if {
    result.high_count > data.params.max_high  # fails silently if max_high is absent
    msg := ...
}

allow if { count(violations) == 0 }
```

If `data.params.max_high` is absent, the `violations` rule body fails silently, the set stays empty, and `allow` fires. A misconfigured params file grants compliance rather than denying it.

**Testing locally with `opa eval`**

You can test a policy on your machine without a real trail using [`opa eval`](https://www.openpolicyagent.org/docs/cli#eval), which needs [OPA installed](https://www.openpolicyagent.org/docs#1-download-opa). Create a minimal input file:

```shell
cat > scan-input.json << 'EOF'
{
  "trail": {
    "compliance_status": {
      "artifacts_statuses": {
        "dashboard": {
          "attestations_statuses": {
            "snyk-container-scan": {
              "processed_snyk_results": {
                "results": [{"high_count": 2, "medium_count": 5}]
              }
            }
          }
        }
      }
    }
  }
}
EOF
```

Save the thresholds for each environment as params files:

```shell
echo '{"max_high": 5, "max_medium": 10}' > params-staging.json
echo '{"max_high": 0, "max_medium": 3}' > params-prod.json
```

Evaluate with permissive staging thresholds. `--data params:params-staging.json` loads the file under `data.params`, where Kosli puts the params of an evaluation:

```shell
opa eval --format pretty \
  --input scan-input.json \
  --data snyk-severity-threshold.rego \
  --data params:params-staging.json \
  '{"allow": data.policy.allow, "violations": data.policy.violations}'
```

```json
{
  "allow": true,
  "violations": []
}
```

Apply stricter production thresholds:

```shell
opa eval --format pretty \
  --input scan-input.json \
  --data snyk-severity-threshold.rego \
  --data params:params-prod.json \
  '{"allow": data.policy.allow, "violations": data.policy.violations}'
```

```json
{
  "allow": false,
  "violations": [
    "artifact 'dashboard': 2 high-severity vulnerabilities exceed limit of 0",
    "artifact 'dashboard': 5 medium-severity vulnerabilities exceed limit of 3"
  ]
}
```

Now verify the fail-safe: omit `max_high` from params entirely:

```shell
echo '{"max_medium": 10}' > params-missing-high.json
```

```shell
opa eval --format pretty \
  --input scan-input.json \
  --data snyk-severity-threshold.rego \
  --data params:params-missing-high.json \
  '{"allow": data.policy.allow, "violations": data.policy.violations}'
```

```json
{
  "allow": false,
  "violations": []
}
```

`allow` is `false` even though no violation message was produced. The missing param causes the compliance check to fail, not to vacuously pass. Always verify this explicitly when writing a policy that relies on params.

Pass the same params files to `kosli evaluate policy` with the `@` prefix. Parameters are always available as `data.params` in the policy:

```shell
kosli evaluate policy \
  --path snyk-severity-threshold.rego \
  --context trail=my-flow/44ca5fa2630947cf375fdbda10972a4bedaaaba3 \
  --params @params-prod.json
```

</Step>

<Step title="Explore the policy input">

When writing policies, it helps to see exactly what data is available. Every evaluation has an ID. Run the evaluation with `--output json` to print it as Kosli returns it, including its `id`:

```shell
EVALUATION_ID=$(kosli evaluate policy \
  --path snyk-no-high-vulns.rego \
  --context trail=my-flow/44ca5fa2630947cf375fdbda10972a4bedaaaba3 \
  --output json | jq --raw-output '.id')
```

Then use [`kosli get evaluation`](/client_reference/kosli_get_evaluation) with `--show-input` to read the input the policy received. Pipe it through `jq` to explore the structure:

```shell
kosli get evaluation "$EVALUATION_ID" \
  --show-input \
  --output json | jq '.input.trail | keys'
```

```plaintext
[
  "compliance_status",
  "created_at",
  "flow_name",
  "moment_number",
  "template_id",
  "trail_name"
]
```

From there, explore `.input.trail.compliance_status` to find the attestation fields your policy can read.

<Info>
See [Replaying an evaluation](/policy-reference/rego_policy#replaying-an-evaluation) to write the input, params and policy of an evaluation to a directory and replay it with OPA.
</Info>

</Step>

<Step title="Use in CI/CD">

By default, `kosli evaluate policy` prints the result and exits with `0` whether the policy allows or denies. Add `--assert` to exit with `1` when the policy denies, which makes it a pipeline gate. An evaluation that fails also exits with `1`. See the [Rego Policy reference](/policy-reference/rego_policy#results-and-exit-codes) for details.

```shell
# Example: gate a deployment on policy evaluation
if kosli evaluate policy \
  --path policies/pr-approved.rego \
  --params '{"pr_attestation_name": "pull-request"}' \
  --context trail="$FLOW_NAME/$GIT_COMMIT" \
  --assert; then
  echo "Policy passed, proceeding with deployment"
  # ... deploy commands ...
else
  echo "Policy denied, blocking deployment"
  exit 1
fi
```

This pattern lets you enforce custom compliance rules as part of your delivery pipeline, using the same trail data that Kosli already collects.

</Step>

<Step title="Record the evaluation">

After evaluating a trail, you can record the result in Kosli as an audit record.

If the policy decides a [control](/tutorials/working_with_controls), publish it with `kosli publish rego-policy` and evaluate it with `--identifier` and `--control`. Kosli records the outcome as a decision against that control, in the `--flow` and `--trail` you name. Only a published policy can record a decision. See [Working with controls](/tutorials/working_with_controls) for the full workflow.

Otherwise, record the result as a generic attestation. This step requires write access to your Kosli org. The examples below use variables you'd set in your CI/CD pipeline, and `my-policy.rego` as a placeholder for your own policy file:

```shell
# Run the evaluation and save the result as JSON
kosli evaluate policy \
  --path my-policy.rego \
  --context trail="$FLOW_NAME/$TRAIL_NAME" \
  --output json > eval-report.json

# Read the allow/deny result from the report
is_compliant=$(jq --raw-output '.result.allow' eval-report.json)

# Extract violations as structured user-data
jq '{violations: (.result.outputs.violations // [])}' eval-report.json > eval-violations.json

# Attest the result
kosli attest generic \
  --name opa-evaluation \
  --flow "$FLOW_NAME" \
  --trail "$TRAIL_NAME" \
  --org "$KOSLI_ORG" \
  --compliant="$is_compliant" \
  --attachments my-policy.rego,eval-report.json \
  --user-data eval-violations.json
```

This creates a generic attestation on the trail with:

* **`--compliant`** set based on whether the policy allowed or denied, read from the JSON report
* **`--attachments`** containing the Rego policy (for reproducibility) and the JSON evaluation report, which includes the evaluation ID so you can read its input later with `kosli get evaluation`
* **`--user-data`** containing the violations, which appear in the Kosli UI as structured metadata on the attestation

<Warning>
Use `--compliant=value` (with `=`) not `--compliant value` (with a space). Boolean flags in Kosli CLI require the `=` syntax when passing `false`. Otherwise `false` is interpreted as a positional argument.
</Warning>

</Step>

</Steps>

## What you've accomplished

You have written OPA/Rego policies using the three design rules that prevent false-positive compliance results: fail-safe default, compliance via positive assertion, and violations as diagnostics only. You've evaluated Kosli trails against those policies with `kosli evaluate policy`, tested safety properties locally with `opa eval`, and recorded evaluation results as attestations.

From here you can:
* Explore evaluated trails in the [Kosli app](https://app.kosli.com)
* Gate deployments in CI/CD pipelines using `kosli evaluate policy --assert`
* Use environment-specific params files to enforce different thresholds per environment
* Publish your policies and record decisions against [controls](/tutorials/working_with_controls)
* Extend your policies to check other attestation types. See [`kosli evaluate policy`](/client_reference/kosli_evaluate_policy) for the full flag reference
